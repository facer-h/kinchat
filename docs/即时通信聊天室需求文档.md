## 1. 产品概述

### 1.1 项目背景

本产品是一个基于网络的实时通信聊天室系统，采用**免注册的昵称进入模式**，支持**在线私聊（仅限在线用户）、群聊、会话级联系人管理、在线状态感知（心跳机制）**等核心能力。产品定位为轻量级即时通信工具，采用纯内存存储方案，**不引入数据库、不设账号体系**，从而大幅降低部署门槛与维护成本，适用于局域网通信、教学演示、小型兴趣社区等场景。

### 1.2 产品目标

1. 提供低延迟、高可靠的实时消息收发体验；
2. 免注册、免配置，用户输入昵称即可开聊；
3. 围绕"在线用户列表 → 私聊 → 群聊"构建完整的实时社交闭环；
4. 通过心跳机制实现准确、及时的在线状态管理——在线状态是本产品的身份基础；
5. 保持架构轻量：零数据库依赖、部署简单、易于二次开发。

### 1.3 术语定义

| 术语 | 说明 |
|---|---|
| 昵称（临时身份） | 用户进入聊天室时提交的唯一名称，是其在聊天室内的身份标识；不持久化，重新进入时重新提交 |
| 心跳（Heartbeat） | 客户端周期性向服务器发送的保活数据包，用于维持长连接并判断在线状态 |
| 在线 / 已离开 | 服务器基于心跳超时对用户连接状态的判定结果；判定为离线后从在线用户列表中移除 |
| 单聊 / 私聊 | 两个**在线**用户之间一对一的实时聊天；目标用户已离开时为非法操作 |
| 群聊 | 所有在线用户所在的公共聊天室（或多个群组）中的多人实时聊天 |
| 会话级联系人 | 用户本次连入期间添加的联系人，仅保存在内存中，离开聊天室后清空 |
| 长连接 | 客户端与服务器之间保持持续的通信通道（WebSocket / TCP） |

## 2. 市场分析

### 2.1 市场规模与趋势

- **市场基础**：即时通信是全球渗透率最高的互联网基础应用之一，全球头部 IM 产品（WhatsApp、微信等）月活跃用户均达数十亿量级，用户对"实时沟通"已成为刚性需求。
- **趋势一：场景细分**。通用 IM 市场高度集中，但局域网/内网通信、游戏社交、兴趣社区等垂直场景持续涌现新机会。
- **趋势二：隐私与内网需求**。部分组织（保密单位、实验室、企业内网）需要数据不出内网、可自部署的轻量通信工具。
- **趋势三：轻量化部署**。小型团队与个人开发者倾向选择无外部依赖、开箱即用的通信方案，而非重量级企业套件；免注册的即开即聊模式进一步降低使用门槛。
- **趋势四：教学与课程需求**。网络编程、即时通信原理是计算机专业经典教学课题，市场长期存在对"轻量可讲解的 IM 实现"的需求。

### 2.2 目标市场定位

| 细分市场 | 需求特征 | 与本产品契合度 |
|---|---|---|
| 教学演示 / 课程设计 | 结构清晰、无复杂依赖、可讲解 | ★★★★★ |
| 局域网 / 内网轻量沟通 | 自部署、免注册、即开即聊 | ★★★★☆ |
| 小型兴趣社区 / 技术验证 | 核心功能够用、易于二次开发 | ★★★☆☆ |

## 3. 竞品分析

### 3.1 主要竞品对比

| 竞品 | 定位 | 优势 | 劣势 / 与本产品差异 |
|---|---|---|---|
| 微信 | 国民级综合 IM | 生态完整、用户基数大 | 需注册认证、体量重、封闭、不可自部署，依赖云端与数据库 |
| QQ | 面向年轻用户的综合 IM | 功能丰富（群、空间、语音通话） | 需账号体系、功能冗余、技术栈厚重 |
| 钉钉 / 飞书 | 企业协作 IM | 组织管理、审批、文档协作强大 | 绑定组织与账号、个人/小场景过重 |
| Telegram | 开放型全球 IM | 多端同步、Bot 开放、加密 | 依赖公网与云端服务器，扩展开发成本高 |
| Discord | 游戏/社区社交通信 | 语音频道、社区运营功能强 | 需账号、功能超出轻量需求，内网不可用 |
| IRC / 传统聊天室 | 经典开放协议聊天室 | 极轻量、免注册（昵称制）、协议开放 | 体验老旧、无现代 UI，联系人/在线状态能力弱 |

### 3.2 竞品启示与差异化定位

- **差异化核心**：轻量、零数据库依赖、免注册昵称制（类 IRC 的极简接入体验 + 现代实时交互体验）、可自部署（含局域网），聚焦"在线列表 + 私聊 + 群聊 + 心跳"核心链路；
- **取舍策略**：明确"无账号、无持久化"不是缺陷而是定位——以极低的使用与部署成本换取即开即聊体验，预留持久化与账号体系的扩展口；
- **竞品参考点**：借鉴 Discord 的频道式群聊交互、IRC 的免注册加入机制、微信的简洁消息流设计。

## 4. 用户分析

### 4.1 目标用户群体

1. **学生 / 开发者（主要用户）**：学习即时通信原理、完成课程设计或毕业设计，需要可运行、可讲解、可扩展的项目；
2. **内网 / 局域网团队**：需要在无法访问公网的网络中自部署一个免注册、即开即聊的轻量沟通工具；
3. **小型社区组织者 / 技术爱好者**：希望搭建属于自己的小型聊天室，并进行二次开发。

### 4.2 用户画像

| 画像 | 典型特征 | 核心诉求 |
|---|---|---|
| 小李（计算机专业学生） | 熟悉命令行与基础网络知识 | 代码结构清晰、原理可讲解、跑起来就能演示 |
| 王工（实验室工程师） | 内网环境、无法连公网 | 一键部署、免注册即开即聊、数据不出内网 |
| 阿杰（兴趣社群管理员） | 技术爱好者、业余维护 | 核心聊天功能稳定、能按需加功能 |

### 4.3 核心使用场景

1. 用户输入昵称进入聊天室，立即看到所有在线用户；
2. 用户从在线用户列表选择对象，发送实时私聊消息；
3. 用户在公共聊天室与多人群聊、接收他人广播消息；
4. 用户将常聊对象加入会话级联系人，通过在线状态判断对方是否可即时沟通；
5. 用户长时间挂机，系统依靠心跳保持在线状态、及时剔除异常掉线连接。

### 4.4 用户需求与痛点

| 痛点 / 需求 | 对应功能方向 |
|---|---|
| 消息延迟高、收不到消息 | 长连接 + 服务器实时推送（私聊/群聊） |
| 不知道对方在不在、能不能聊 | 心跳机制 + 实时在线用户列表与状态展示 |
| 注册、登录、记密码太麻烦 | 免注册昵称进入，即开即聊 |
| 常用的聊天对象不好找 | 会话级联系人列表 + 搜索 |
| 部署太重（要装数据库、要配一堆环境） | 无数据库内存存储、开箱即用 |
| 网络不好时被误判离线 / 掉线后无法恢复 | 心跳容错阈值 + 断线后自动重新加入 |

### 5.3 按优先级划分的功能列表

#### 5.3.1 核心功能（P0）

| 功能 | 简要说明 |
|---|---|
| 进入聊天室（昵称认证） | 用户连接服务器后提交昵称进入聊天室；服务器校验昵称非空、格式合法且**未被当前在线用户占用**；通过后加入在线用户列表并建立长连接 |
| 离开聊天室（登出） | 用户主动断开连接、从在线用户列表移除、通知其他用户状态变更 |
| 心跳保活 | 客户端按固定间隔（默认 30s，可配置）向服务器发送心跳包，服务器收到后刷新该用户的心跳时间戳 |
| 在线 / 已离开状态判定 | 服务器定时扫描各连接的最后心跳时间；超过阈值（如 3 个心跳周期）判定为已离开 |
| 连接超时自动下线 | 被判超时 / 连接异常断开的用户，由服务器主动清理连接、从在线列表移除并回收资源 |
| 一对一私聊（仅在线用户） | 用户选择**在线用户**发送文本消息，服务器实时推送到对方；目标用户已离开时服务器拒绝并返回"对方已离开聊天室"提示 |
| 群聊 / 公共聊天室 | 所有在线用户默认加入公共聊天室；消息由服务器实时广播给所有在线成员，展示发送者昵称与时间 |
| 在线用户列表 | 实时展示当前所有在线用户及其状态，是发起私聊、添加联系人的入口 |
| 会话级联系人列表 | 展示本次会话内添加的联系人；离开聊天室后清空 |
| 添加 / 删除会话级联系人 | 从在线用户列表中选择用户添加为会话级联系人，也可随时删除 |
| 联系人实时在线状态 | 会话级联系人列表中实时展示对方状态：在线 / 已离开（由心跳机制驱动，对方离开后保留记录并标记状态） |
| 并发在线支持 | 服务器支持多个客户端同时在线并彼此通信（≥ 100 并发，见非功能需求） |
| 合法性校验 | 未经昵称认证的连接不能收发消息；私聊目标必须是当前在线用户；消息类型/格式非法时拒绝处理 |

#### 5.3.2 非核心功能（P1）

| 功能 | 简要说明 |
|---|---|
| 会话内修改昵称 | 用户在本次会话中可更换昵称，需校验新昵称未被占用，并向聊天室广播变更 |
| 断线后自动重新加入 | 网络抖动导致连接断开后，客户端可在短时间内自动用原昵称重新加入（昵称未被占用时）；被占用则提示改用新昵称 |
| 会话历史记录 | 服务器为每个活跃会话缓存最近 N 条消息（内存），用户进入会话可拉取近期记录 |
| 在线用户 / 联系人搜索 | 在在线用户列表与联系人列表中按昵称模糊搜索 |
| 进入 / 离开聊天室广播 | 用户进入或离开聊天室时，向全体在线用户（或公共聊天室）推送通知 |
| 系统公告 / 广播消息 | 服务器（管理员）可向全体在线用户发布公告类消息 |
| 未读消息提醒 | 非当前会话收到新消息时，展示未读角标与数量 |

#### 5.3.3 拓展功能（P2）

| 功能 | 简要说明 |
|---|---|
| 消息撤回 | 发送者在限定时间内（如 2 分钟）可撤回消息，双方及群内均不可见 |
| 表情包 / Emoji | 消息中支持发送 Emoji 与常用表情 |
| 图片 / 文件传输 | 私聊及群聊中支持发送图片与文件（服务器中转或点对点） |
| 联系人分组 | 会话级联系人支持自建分组（如：同学、同事） |
| 消息已读回执 | 单聊中展示"已读/未读"状态 |
| 自定义建群与群管理 | 用户可创建自定义群组，支持群主管理、成员邀请与移出 |
| 传输加密 / 消息加密 | 链路启用 TLS；可选端到端消息加密 |
| 敏感词过滤 / 禁言 | 对群聊消息做敏感词过滤，管理员可对违规用户禁言 |
| 本地文件持久化 | 将聊天记录、联系人快照等数据定期持久化到本地文件（JSON 等），实现重启后部分数据可恢复 |

### 5.4 关键业务流程

#### 5.4.1 进入聊天室（F-A1）

```
客户端 ──连接服务器──▶ 提交昵称
                          │
            服务器校验：非空 / 格式合法 / 未被占用
                          │
        失败：返回错误并提示更换昵称
        成功：加入在线用户列表 ──▶ 建立长连接 ──▶ 广播"xx 进入聊天室"
                          │
                    启动心跳保活
```

#### 5.4.2 心跳与在线状态（F-B1 / F-B2 / F-B3）

```
客户端 ──每 30s──▶ 心跳包 ──▶ 服务器更新"最后心跳时间"
                                   │
服务器扫描：超过 90s（3 个周期）未收到心跳
                                   │
         判定为已离开 ──▶ 清理连接────▶ 从在线用户列表移除
                                   │
                    联系人列表中标记为"已离开"，广播离开通知
```

- 心跳间隔与超时阈值均可配置；
- 客户端主动离开时发送离开通知，立即更新状态，不必等待超时。

#### 5.4.3 私聊消息流（F-C1）

```
发送方 ──发送消息──▶ 服务器（校验昵称认证 + 消息格式）
                          │
             目标在线：实时推送到接收方 ──▶ 接收方展示
             目标已离开：拒绝并返回"对方已离开聊天室"
```

#### 5.4.4 群聊消息流（F-C2）

```
发送方 ──发送消息──▶ 服务器（校验昵称认证 + 消息格式）
                          │
                    遍历所有在线成员，逐一直发消息
                          │
                  各成员接收并展示（含发送者昵称、时间）
```

#### 5.4.5 添加会话级联系人流程（F-D3）

```
用户 A ──在线用户列表选择用户 B──▶ 服务器校验 A、B 均在在线列表
                          │
            将 B 写入 A 的会话级联系人列表 ──▶ A 端列表刷新并展示 B 的状态
                          │
    B 之后离开聊天室：联系人记录保留，状态标记为"已离开"，不可再向其发私聊
```

## 6. 非功能需求

| 类别 | 需求项 | 指标 / 说明 |
|---|---|---|
| 性能 | 消息实时性 | 局域网环境下，消息端到端延迟 ≤ 100ms（P95） |
| 性能 | 心跳处理 | 服务器心跳处理开销低，100 并发下 CPU 占用无明显波动 |
| 容量 | 并发在线 | 单服务器支持 ≥ 100 个并发在线用户（内存存储模型） |
| 可靠性 | 服务稳定性 | 支持 7×24 小时连续运行，崩溃后具备快速重启恢复能力 |
| 可靠性 | 状态准确性 | 心跳误判率低：阈值取 3 个心跳周期，兼顾网络抖动与及时性 |
| 可靠性 | 掉线恢复 | 网络恢复后客户端能自动重新加入聊天室（P1 实现） |
| 安全 | 身份与输入校验 | 昵称唯一性校验、消息长度与格式校验，防止非法输入注入异常状态 |
| 安全 | 通信安全 | 预留传输加密能力（TLS）；内网部署场景为默认安全域 |
| 易用性 | 操作路径 | 核心任务（进入聊天室、发消息、加联系人）操作不超过 3 步 |
| 易用性 | 状态可见 | 在线列表实时刷新、消息发送结果（成功/对方已离开）均有明确反馈 |
| 可维护性 | 架构 | 连接管理、消息路由、用户管理模块化分离，便于讲解与二次开发 |
| 可移植性 | 运行环境 | 跨平台（Windows / Linux / macOS），后端部署仅需单机 + 运行时环境 |

## 7. 技术约束与设计说明

### 7.1 不使用数据库的约束与应对

| 约束点 | 设计应对 |
|---|---|
| 无账号体系，身份无持久性 | 身份为一次性昵称：进入时提交，服务器校验唯一性；每次进入重新提交昵称 |
| 数据不持久化，重启全清空 | 产品定位明确为轻量会话型工具；用户、联系人、消息均在内存中维护 |
| 联系人仅会话级 | 联系人列表随会话建立、随离开清空；对方离开后仅标记状态不删除记录（本会话内） |
| **只能与在线用户聊天** | 私聊目标必须在线，服务器强制校验；不存在离线消息（离线消息需持久化能力，超出无数据库约束） |
| 无法依赖 SQL 查询 | 采用语言内置数据结构（Map / List 等）管理在线用户、会话语义、联系人索引 |
| 历史记录能力受限 | 仅提供会话级内存缓存（P1）；完整持久化作为拓展功能（P2，JSON 文件或未来接入数据库） |
| 大规模数据扩展受限 | 明确容量目标为小型场景（≥ 100 并发）；架构预留存储层抽象，未来可平滑接入数据库与账号体系 |

### 7.2 通信协议建议

- 长连接：WebSocket（浏览器/通用客户端友好）或原生 TCP；
- 消息格式：JSON 结构化协议，按消息类型区分：
  - 进入：`{type: "join", nickname}`
  - 离开：`{type: "leave"}`
  - 心跳：`{type: "heartbeat"}`
  - 私聊：`{type: "private_msg", to, content}`
  - 群聊：`{type: "group_msg", content}`
  - 系统广播：`{type: "system_msg", content}`；
- 服务器对每种消息类型做合法性校验（未认证连接、目标离线、格式非法等情况拒绝处理并回错误响应）。

### 7.3 心跳参数建议（可配置）

| 参数 | 建议值 | 说明 |
|---|---|---|
| 心跳间隔 | 30s | 客户端定时发送心跳的周期 |
| 超时阈值 | 90s（3 个周期） | 超过该时长未收到心跳即判定已离开 |
| 服务器扫描周期 | 10s | 服务器检查各连接最后心跳时间的频率 |

## 9. 风险分析

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 无账号无持久化，重启全丢 | 重启后在线用户、联系人、消息全部清空，身份重置 | 明示产品定位；M3 可选实现本地文件持久化；预留存储层抽象接口 |
| 昵称冒用 / 无身份认证 | 他人可冒充先前用户的昵称 | 冒用仅限在线唯一性校验，不涉及数据泄露（无私人数据）；预留接入账号体系的扩展方向 |
| 心跳误判（网络抖动） | 在线状态不准确，用户"假离开" | 超时阈值取 3 个心跳周期；M2 实现断线自动重入兜底 |
| 并发过高内存吃紧 | 在线人数超载时性能下降甚至崩溃 | 明确容量目标（≥100 并发）；超时连接及时清理；必要时增加限流 |
| 明文传输被窃听 | 消息在网络上可被截取 | 内网部署默认安全域；预留 TLS/加密（P2） |
| 单点故障 | 服务器宕机导致服务整体不可用 | 文档化快速重启方案；架构预留多实例/集群化演进方向 |

## 10. 验收标准（M1 核心功能）

1. 用户输入昵称即可进入聊天室，**无需注册**；空昵称、非法昵称、已被占用的昵称均被拒绝并提示；
2. 在线用户列表实时反映所有人的进入与离开（含主动离开与心跳超时）；
3. 两个在线用户可互发私聊，消息在 **1 秒内** 送达并正确展示；**向已离开用户发私聊被服务器拒绝**并提示"对方已离开聊天室"；
4. 群聊中任意成员发言，所有在线成员均能实时收到，正确展示发送者昵称与时间；
5. 客户端保持心跳可长时间在线；拔网线/杀进程后，服务器在超时阈值内将其判定为已离开并从在线用户列表移除，其他人端侧实时看到变化；
6. 可从在线用户列表添加/删除会话级联系人，对方离开后联系人记录保留并标记"已离开"；
7. 用户离开聊天室后，连接与会话被清理，不再出现在任何人的在线列表中；
8. 服务器单机支持 ≥ 100 个并发连接，消息延迟与心跳判定不受影响。
